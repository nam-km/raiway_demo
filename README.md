# Raiway browser demo

The Raiway wheel-legged perceptive policy, trained in RaiSim2 (`raisimGymForSegway`), running live in the browser:
MuJoCo WASM (`@mujoco/mujoco`) for physics, onnxruntime-web for the policy and three.js for rendering. Nothing
runs on a server; the built `dist/` is a static site.

## Run

```bash
npm install
npm run dev          # http://localhost:5173
npm run build        # static site in dist/ with relative paths, so any subdirectory works (e.g. GitHub Pages)
```

Controls: W/S or ↑/↓ drive, A/D or ←/→ turn, R resets, or use the on-screen joystick. The drive keys reach the
robot even while a slider or a menu has focus. The command is a velocity command (vx, wz), the same
interface the policy sees in both training episode types.

The Policy menu lists the exported checkpoints. Choosing one swaps the controller in place and resets the robot;
the terrain and the sliders stay as they are.

The terrain level slider (default 1) uses the training formulas of `Environment.hpp` and
`RandomHeightMapGenerator.hpp`, so level 1 is the hardest terrain the curriculum reaches:

- Stairs: step height 0.02 + 0.28·level (0.30m at level 1), tread max(height / tan 35°, 0.3) + 0.1m, eight steps
  up from 0.75m past the spawn, a 2m landing, then eight steps down. Training has no descent on this terrain.
- Steps: square blocks with heights U(0, 0.05 + 0.25·level) (up to 0.30m at level 1), as in `STEPS`. Training
  samples the block width from U(0.3, 0.5)m per episode; here it is 0.4m. Training has no flat spawn zone either.
- Holes: depth 0.05 + 0.75·level², two independent 3m lanes with gaps U(0.4, 0.7)m, landings U(0.3, 0.6)m and
  landing heights U(-0.1, 0.1)m, and a flat 1.5m spawn strip.
- Hurdles: 0.05m thick, from 1m past the spawn, as in `HURDLES`, but 1.5m apart (the middle of the `TUK` spacing)
  rather than 1m. Their height follows the `TUK` formula, 0.02 + 0.28·level (0.30m at level 1), since `HURDLES`
  itself is not in the training mix.

## Policies

`public/model/` is generated by `raisimGymForSegway/raisimGymForSegway/sim2sim/export_demo.py`; do not edit it
by hand. The script needs `mujoco`, `onnx` and `onnxruntime` in the raisim Python environment.

```bash
cd ../raisimGymForSegway/raisimGymForSegway/sim2sim
python export_demo.py -w <RUN>/full_XXX.pt [-l "menu label"] [--default]   # writes ../../../raiway_demo/public/model (-o overrides)
python sim2sim.py -t stairs -l 1.0 --vx 1.0 [-p <policy>] [--view]         # Python MuJoCo rollout; terrains: flat, stairs, steps, holes, hurdles
```

Each export adds or replaces one folder, `policies/<name>/` with `policy.onnx` and `config.json`, and its entry in
`policies.json`; the name is the run directory unless `-n` gives another. `--default` marks the policy the page
starts with, which is also what `sim2sim.py` and `test:headless` use when no policy is named. To drop a policy,
delete its folder and its `policies.json` entry. `raiway.xml` and `meshes/` are shared, so every policy has to be
for the same robot model and simulation time step.

- `policy.onnx`: one graph with inputs `obs` (raw actor observation), `est_input` (raw estimator history) and
  `command` (vx, wz), and outputs `action` and the denormalized `estimate`. The observation and estimator-input
  normalization is baked in, so callers pass unnormalized values.
- `raiway.xml`: the URDF converted to MJCF at the nominal wheel parameters, with `rotor_inertia` as armature.
- `meshes/`, `config.json`: visual meshes; dims, scan layout, PD gains and action scaling.

Line and ring actor scans are both supported; the layout is read off the checkpoint's normalizer.

## Differences from RaiSim

Every randomization is left out, the URDF ones included. Beyond that:

- Contacts use MuJoCo's default soft-contact parameters, with an elliptic friction cone and `impratio` 10 to limit
  wheel creep; with the default pyramidal cone the stairs descent at 1.5 m/s falls.
- The terrain is an hfield on the same 0.02m grid as training, and the height scan reads it bilinearly.
- The wheel's axle inertia is kept; its other two diagonal terms are raised to satisfy MuJoCo's triangle inequality.
- There is no restitution: MuJoCo has no restitution coefficient, and emulating one by switching the contact
  damping at touchdown produced unnatural rebounds, so impacts follow MuJoCo's contact model.

On flat ground the `2026-09-25-10-42-26-5444` checkpoint (`full_50000.pt`) tracks the same velocity as in RaiSim
(vx 1.00 m/s in MuJoCo and 1.01 m/s in RaiSim for a 1.0 m/s command), and the JS and Python ports agree to four
digits there; on stairs they drift apart slowly, as the rollout amplifies rounding differences at the step edges.

With that checkpoint, at level 1 the robot crosses stairs, steps, holes and hurdles for 10s at both 1.0 and 1.5 m/s. On flat ground a 2.0 rad/s
turn command is tracked at 2.0 rad/s at 1.0 m/s and at 1.8 rad/s at 1.5 m/s. With the hurdles 1m apart the robot
cleared five at 1.0 m/s and then turned away along the row, which is why they are 1.5m.

## Layout

- `src/sim.js`: MuJoCo stepping, PD control, the actor observation, estimator history and
  termination. It is a line-by-line port of `sim2sim/raiway_mujoco.py`; a change to the actor observation, scan
  layout or action scaling in the training repo has to be mirrored in both.
- `src/terrain.js`: terrain grids, parameterized by terrain level, that drive both the hfield and the height scan.
  The hfield spans -1m to 3m. `sim2sim/terrain.py` matches it except for the random layouts of `steps` and `holes`.
- `src/render.js`: three.js scene built from the compiled MuJoCo model.
- `src/main.js`: loading, UI, command input, policy switching and the real-time loop.

## Checks

```bash
npm run test:headless -- stairs 1.0 0 10 1.0   # terrain vx wz seconds [level] [policy]; Node, no browser
npm run test:browser                       # builds, drives each policy in headless Chrome, writes test/screenshot.png
```

`test:headless` prints the same metrics as `sim2sim.py`, so the two ports can be compared directly.
